## API 문서: springdoc-openapi

날짜: 2026-09-27 · Step에 속하지 않음

**문제**

API를 눌러 보려면 curl이나 테스트 코드를 써야 했다. 요청 형태와 응답을 한곳에서 보고 바로 호출해 볼 화면이 필요하다.

**대안**

| 대안 | 방식 |
|---|---|
| springdoc-openapi | 실행 중인 앱이 컨트롤러를 읽어 OpenAPI 문서와 Swagger UI를 만든다 |
| Spring REST Docs | 테스트가 통과할 때 요청·응답 조각을 만들고, 그걸 모아 문서를 만든다 |
| 문서 없음 | 지금처럼 테스트 코드와 curl로 본다 |

**선택 이유**

- 의존성 한 줄로 기존 컨트롤러가 모두 문서에 잡힌다. 학습 초점(동시성·모듈 경계)에서 벗어나는 작업이 적다
- 브라우저에서 바로 선점·결제를 호출해 볼 수 있다
- Boot 4.1용 버전(3.1.1, Boot 4.1.0 기준 빌드)이 나와 있다

**포기한 것**

- **테스트로 보장되는 문서.** REST Docs는 테스트가 통과해야 문서가 나오므로 문서가 코드와 어긋날 수 없다. springdoc은 코드에서 추론하므로, 응답 예시나 설명은 어긋날 수 있다
- **에러 응답 문서.** `@RestControllerAdvice`가 내보내는 ProblemDetail(`code` 포함)은 자동으로 문서에 잡히지 않는다. 필요해지면 따로 설정한다
- 라이브러리 하나를 더 따라가야 한다. Boot 메이저 버전을 올릴 때 springdoc 호환 버전을 함께 찾아야 한다 (2.x → 3.x가 그랬다)

**검증**

- 확인한 범위: `ApiDocsTest`가 `/v3/api-docs`에 `POST /reservations`가 있는지, `/swagger-ui/index.html`이 200인지 본다. 의존성 없이 돌리면 둘 다 실패하는 것을 확인했다
- 못 한 범위: 문서의 요청·응답 스키마가 실제 API와 맞는지는 하나하나 보지 않았다
- Step 4에서 `userId`가 요청 본문에서 빠지면 Swagger UI에서 사용자를 넣는 방법(헤더 등)을 다시 정해야 한다

## 도메인: 회차(Schedule)를 뺀다

날짜: 2026-10-04 · Step에 속하지 않음 (Step 2 진행 중에 정함)

**문제**

공연 → 회차 → 좌석 → 예약 구조에서 좌석 행은 공연에 붙어 모든 회차가 함께 쓰고, 팔리는 단위는 "회차 + 좌석" 쌍(`ScheduledSeat`)이었다.
그래서 "이 좌석이 팔렸는가"를 말할 때마다 회차를 함께 들고 다녀야 하고, 선점할 때 "이 좌석이 이 회차의 공연 좌석인가"를 따로 검증해야 했다.
학습 초점(동시성·모듈 경계)에 비해 도메인이 복잡하다.

**대안**

| 대안 | 방식 |
|---|---|
| 회차 유지 | 지금 구조. 재고 단위는 "회차 + 좌석" |
| 회차를 빼고 시작 시각은 공연으로 | 공연 = 한 번의 상연. 공연에 `startAt`을 둔다 |
| 회차와 시작 시각을 모두 뺀다 | 공연 = 한 번의 상연. 시각 개념이 없다 |

**선택 이유**

- 재고 단위가 좌석 하나가 된다. 선점은 "좌석 ID로 예약 하나 만들기"가 되고, 회차 조회·`seat.isIn(schedule)` 검증이 사라진다
- Step 2에서 이중 선점을 막을 지점(유니크 제약·락을 걸 행)이 좌석 하나로 분명해진다
- 시작 시각은 "시작 전 기한까지만 취소" 규칙에만 쓰였다. 시각 비교일 뿐 새 경합을 만들지 않으므로 함께 뺀다

**포기한 것**

- **현실적인 모델.** 실제 예매는 같은 공연을 여러 날짜에 판다. 같은 좌석이 회차마다 따로 팔리는 상황은 이제 표현할 수 없다
- **취소 기한 규칙.** Step 9(취소·환불)에서 "기한이 지난 취소"를 거절하는 경우가 없어진다
- **Step 11의 "인기 회차"** 는 "인기 공연"이 된다. 부하가 몰리는 단위가 공연 하나라 측정에는 차이가 없다
- 다시 회차를 넣으려면 예약의 재고 키를 좌석 → "회차 + 좌석"으로 되돌려야 한다. Step 2의 유니크 제약·락 대상도 함께 바뀐다

**검증**

- 확인한 범위: 바꾸는 동안 커밋마다 `./gradlew build`가 통과하게 한다 (새 메서드 추가 → 호출부 전환 → 옛 것 삭제). 스키마는 V5(컬럼 nullable)·V6(테이블·컬럼 삭제)로 바꾸고 V1·V2는 건드리지 않는다
- 못 한 범위: Step 0·1의 `PROGRESS.md` 기록은 회차가 있던 시점의 이력이라 고치지 않는다. 그 기록의 API·도메인 설명은 지금과 다르다
