## Step 0 — 그냥 동작하게 만든다

기간: 2026-09-17 ~ 2026-09-27

### 목표

좌석을 조회하고, 선점하고, 결제하고, 티켓을 받는 흐름을 **모듈·경계·락 없이** 동작하게 만든다.
Step 1 이후에 깨뜨릴 출발점이라 일부러 허술하게 둔다.

### 한 일과 이유

**API**

```
GET  /schedules/{id}/seats          좌석과 예매 가능 여부
POST /reservations                  좌석 선점 → 201 + Location
POST /reservations/{id}/payment     결제 → 확정 → 발권 (항상 성공하는 내부 결제)
GET  /reservations/{id}             예약 + 결제·티켓
GET  /reservations?userId=          내 예매 목록 (요약)
```

**데이터**

- 좌석은 공연에 붙고, 회차마다 따로 팔린다. 좌석 표에 "팔림" 컬럼을 두지 않고, 그 회차·좌석의 예약(HELD·CONFIRMED)이 있는지로 판단한다
- 예약 상태 HELD → CONFIRMED를 한 행에서 바꾼다. 결제·티켓은 예약 표에 붙이지 않고 따로 둔다 — Step 4에서 각자 모듈이 될 자리다
- 외래 키를 두지 않고 ID로만 가리킨다. 테이블 소유가 모듈별로 갈라질 것이라서다
- `(schedule_id, seat_id)`에 유니크 제약을 **일부러 두지 않았다**. 걸면 Step 1에서 재현할 이중 선점이 미리 막힌다. 결제·티켓의 `reservation_id`도 같은 이유로 유니크가 없다
- 만료 시각(`expires_at`)은 선점할 때 박아둔다. 유효 시간 설정이 바뀌어도 이미 만든 선점의 기한이 움직이지 않는다

**동작**

- 선점은 "있는지 조회 → 없으면 저장"이다. 락이 없다 (Step 1에서 재현할 대상)
- 만료는 결제할 때만 판정해 거절한다. 상태를 EXPIRED로 바꾸거나 좌석을 풀어주지 않는다 (Step 3)
- 결제·확정·발권이 한 트랜잭션이다. 모듈이 갈라지면 유지할 수 없는 묶음이다 (Step 4·6·8)
- 시계를 서울로 고정했다(`ClockConfiguration`). `LocalDateTime`은 타임존이 없어, 서버 타임존을 따르면 환경마다 다른 기준의 값이 섞인다
- 사용자는 요청 본문·쿼리 파라미터로 받고 그대로 믿는다. 본인 확인은 결제에만 있고 조회에는 없다 (Step 4에서 사용자를 정하는 위치를 옮긴다)

**에러**

- 도메인 예외 하나에 `BookingErrorCode` 하나. RFC 9457 ProblemDetail에 `code` 속성을 담아, 클라이언트가 문구가 아니라 코드로 구분한다
- 요청 값이 빈 경우(본문 검증 실패, 필수 쿼리 파라미터 누락)도 `INVALID_REQUEST`로 같은 형식을 쓴다

**테스트**

- H2 없이 Testcontainers MySQL 8.0으로 돈다. 테스트는 롤백 대신 매번 새 공연·새 사용자 ID를 만들어 데이터가 섞이지 않게 한다 — Step 1의 동시성 테스트는 커밋된 데이터를 봐야 해서 롤백으로 감쌀 수 없다
- `BookingFlowTest` 하나가 좌석 조회 → 선점 → 결제 → 예약 조회 → 목록을 API만으로 이어서 거친다

## Step 1 — 이중 선점을 재현한다

기간: 2026-09-27

### 목표

Step 0의 선점이 동시 요청에서 실제로 깨지는 것을 **실패하는 테스트로** 드러낸다. 막지는 않는다 (Step 2).

### 한 일과 이유

**관찰 수단 먼저**

동시 요청 N건의 로그와 행이 뒤섞이면 "어디서 깨졌나"에 답할 수 없어서, 재현보다 먼저 갖췄다.

- 요청 ID: `RequestIdFilter`가 요청마다 8자 ID를 만들어 MDC에 넣고 `X-Request-Id`로 돌려준다. 로그 패턴의 추적 ID 자리(`logging.pattern.correlation`)에 찍힌다
  - 스레드 이름만으로는 부족하다. 톰캣이 스레드를 재사용해 같은 이름이 여러 요청에 걸쳐 나온다
  - 클라이언트가 보낸 ID는 쓰지 않는다. 같은 ID를 여러 요청에 보내 로그를 섞을 수 있다
- 행 생성 시각: `reservation.created_at datetime(6)`을 DB가 채운다 (V4). 엔티티는 바꾸지 않았다

**재현**

`DoubleHoldReproductionTest` (`@Tag("reproduction")`)

- MockMvc가 아니라 실제 포트로 띄운 서버에 HTTP로 보낸다. 요청마다 톰캣 스레드가 따로 붙고 필터를 거친다
- 서로 다른 사용자 10명이 같은 회차·같은 좌석에 선점한다. 스레드를 출발선(`CountDownLatch`)에 세웠다가 한 번에 푼다
- 요청 수 10은 커넥션 풀 기본 크기다. 넘기면 일부가 커넥션을 기다리느라 늦게 출발한다
- 이 테스트에서만 SQL 로그를 켜서 요청별 SQL 순서를 요청 ID로 가른다

### 관찰

```
기대: 1건 성공, 9건 실패
실제: 10건 모두 201, 같은 좌석에 HELD 예약 10행
```

4번 돌려 4번 모두 10건 성공이었다. 10행의 `created_at` 간격은 319~436µs.

요청 10건의 SQL만 뽑으면 이렇다 (한 번의 실행).

```
18:33:06.559  10건 모두  exists (이 좌석에 HELD·CONFIRMED 예약이 있나)
18:33:06.562  10건 모두  insert into reservation
```

10건 모두 누군가의 INSERT보다 먼저 확인을 끝냈다. 그래서 모두 "없음"을 보았다.

### 설명

**어느 줄에서 문제가 생기나**

`ReservationService.hold()`의 확인(`existsBySeatAndStatusIn`)과 저장(`save`) **사이**다. 어느 한 줄이 틀린 게 아니다.
확인에서 얻은 "없다"가 저장하는 순간에도 참이라는 보장이 없다.

**"조회해서 없으면 INSERT"가 왜 안전하지 않은가**

- 확인과 저장이 하나의 동작으로 묶여 있지 않다. 그 사이에 다른 요청이 같은 확인을 지나가는 것을 막는 장치가 없다
- DB는 "한 좌석에 살아 있는 예약은 하나"라는 규칙을 모른다. `(schedule_id, seat_id)` 인덱스는 유니크가 아니라, 같은 값의 INSERT 10건을 모두 받는다
- 규칙이 앱의 `if`에만 있고, 그 `if`는 동시에 실행되면 모두 같은 답을 본다

**트랜잭션을 걸었는데 왜 막히지 않나**

트랜잭션은 다른 요청을 기다리게 하는 장치가 아니다. InnoDB 기본 격리 수준은 REPEATABLE READ다.

| 보장하는 것 | 보장하지 않는 것 |
|---|---|
| 커밋 안 된 남의 데이터를 읽지 않는다 | 내가 읽은 조건("예약 없음")이 내가 커밋할 때까지 참이라는 것 |
| 트랜잭션 안에서 같은 조회를 반복하면 같은 결과 (스냅샷) | 남이 그 조건에 맞는 행을 INSERT하지 못하게 막는 것 |
| 내 변경은 전부 반영되거나 전부 취소된다 | 요청들이 차례로 실행되는 것 |

- `exists` 조회는 일반 SELECT라 락을 잡지 않는 스냅샷 읽기다. 남의 커밋 안 된 INSERT가 보이지도 않고, 막지도 않는다
- INSERT 10건은 유니크가 아닌 인덱스에 들어가 서로 충돌하지 않는다. 10개 트랜잭션이 모두 커밋에 성공한다

**그 간격이 겹친 구간에 대해 무엇을 말해주나**

- 요청마다 위험한 구간은 "확인부터 커밋까지"다. 로그상 확인(.559)에서 INSERT(.562)까지만 약 3ms이고, 커밋은 그 뒤다
- INSERT 10건이 0.3ms 안에 몰렸다. 도착 간격이 위험 구간보다 훨씬 좁아 모든 요청의 위험 구간이 서로 겹쳤다. 어느 요청이 거절되려면 그 요청의 확인이 다른 요청의 **커밋 뒤**에 실행됐어야 한다
- `created_at`은 INSERT 문이 **시작한** 시각이지 커밋 시각이 아니다. 319µs는 겹친 구간의 길이가 아니라 요청들이 얼마나 촘촘히 도착했는지를 보여준다
- 위험 구간을 줄이면 충돌이 덜 자주 날 뿐 없어지지 않는다. Step 2는 구간을 줄이는 방법이 아니라 구간을 없애는 방법을 골라야 한다

### 만난 문제

| 문제 | 어떻게 했나 |
|---|---|
| MockMvc 테스트에서 `DispatcherServlet` 로그를 켜도 요청 로그가 안 나옴 | MockMvc는 `TestDispatcherServlet`을 써서 로거 이름이 다르다. 요청 ID 확인은 그 로거로 했다 |
| `created_at`이 µs까지 같은 행이 셋, `id` 순서와 `created_at` 순서가 다름 | MySQL `current_timestamp`는 행이 쓰인 순간이 아니라 SQL 문 시작 시각이다. V4 주석을 고쳤다 |
| `created_at`(DB 세션 시간대)과 `expires_at`(앱 서울 시계)의 기준이 다름 | 행끼리 간격을 재는 데만 쓰고 `expires_at`과 비교하지 않는다고 주석에 적었다 |
| `ReservationService` 주석에 이중 선점 원인이 이미 적혀 있었음 | 설명할 질문의 답이라 빼고, 재현 테스트를 가리키는 문장만 남겼다 |
| Boot 4에서 `@LocalServerPort` 위치를 기억에 의존할 수 없음 | jar를 열어 `org.springframework.boot.test.web.server`인 것을 확인했다 |

### 남겨둔 것

- 재현 테스트는 성공 건수만 본다. 막은 뒤 거절 응답이 409인지(500이 아닌지)는 Step 2에서 함께 본다
- 격리 수준을 SERIALIZABLE로 올리면 InnoDB가 일반 SELECT에도 공유 락을 건다. 결과가 어떻게 달라지는지는 실험하지 않았다
- 결제 행 중복(같은 예약에 결제 둘)은 재현하지 않았다. `created_at`도 `reservation`에만 있다
- 앱 코드가 요청 처리 중 남기는 로그가 거의 없어, 요청 ID가 찍히는 줄은 SQL 로그를 켰을 때가 대부분이다
