# 풀어야 할 문제 목록

**순서대로 진행한다.** 앞의 문제를 겪지 않고 뒤의 장치를 먼저 넣으면,
그 장치가 왜 있는지 나중에 설명할 수 없게 된다.

만들 기능의 범위는 `ai_docs/FEATURES.md`에 있다. 이 문서는 그 기능을 **어떤 순서로, 어떤 문제를 겪으며** 만드는지 적는다.

각 Step의 구성:

- **목표** — 무엇을 만드는가
- **재현** — 무엇이 깨지는 것을 먼저 보아야 하는가 (실패하는 테스트)
- **완료 조건** — 무엇이 되면 끝인가
- **설명할 질문** — 코드 없이 말로 답할 수 있어야 하는 것

> ⚠️ 이 문서는 **정답을 적지 않는다.** 방법을 알려주는 문서가 아니라
> 풀어야 할 문제를 알려주는 문서다. 답이 적혀 있으면 이 프로젝트의 의미가 없다.

## Step 0 — 그냥 동작하게 만든다

- [ ] 완료

**목표**: 좌석을 선점하고, 결제하고, 티켓을 받는 것. **모듈도 경계도 락도 없이.** 한 패키지에 다 넣어도 된다.

도메인 최소 구성:

```
공연(Performance)  회차(Schedule)  좌석(Seat)  예약(Reservation)  결제(Payment)  티켓(Ticket)
```

엔드포인트 예시 (이름과 형태는 바꿔도 된다):

```
GET  /schedules/{id}/seats           회차의 좌석과 예매 가능 여부
POST /reservations                   { scheduleId, seatId, userId } → 좌석 선점
POST /reservations/{id}/payment      결제 → 예약 확정 → 발권
GET  /reservations/{id}
GET  /reservations?userId=           내 예매 목록
```

결제는 아직 내부 처리다 (항상 성공하는 가짜로 충분하다).

**재현**: 없다. 이 Step은 출발점을 만드는 것이다.

**완료 조건**

- 좌석 조회 → 선점 → 결제 → 확정·발권까지 이어지는 테스트 1건이 통과한다
- 이미 선점되었거나 확정된 좌석을 선점하면 거절된다 (**단일 스레드에서만** 확인)
- 선점 유효 시간이 지난 뒤 결제하면 거절된다 (**단일 스레드에서만** 확인)
- `./gradlew test` 통과

**설명할 질문**

- 좌석의 "예매 가능" 상태를 어디에 두었나? 좌석 테이블의 컬럼인가, 예약 테이블의 존재 여부인가?
- 좌석 재고는 회차 단위인가, 좌석 단위인가? 같은 좌석이 회차마다 따로 팔리는 걸 어떻게 표현했나?
- 선점과 확정을 같은 것의 상태로 두었나, 서로 다른 것으로 두었나?
- 이 선택들이 다음 Step(동시성)에 어떤 영향을 주겠는가?

> 💡 이 Step은 **일부러 허술하게** 만든다. 고쳐야 할 것이 있어야 다음 Step이 성립한다.
> 락을 미리 넣지 않는다. 만료된 선점을 **자동으로 풀어주는 처리도 아직 넣지 않는다** (Step 3).

## Step 1 — 이중 선점을 재현한다

- [ ] 완료

**목표**: Step 0의 코드가 **실제로 깨지는 것**을 실패하는 테스트로 드러낸다.

**재현**: 같은 회차의 같은 좌석에 동시 선점 요청 N건. 스레드 여러 개로 동시에 때린다.

```
기대: 1건 성공, N-1건 실패
실제: ?
```

**완료 조건**

- **실패하는 테스트가 있다.** 이게 이 Step의 산출물이다
- 몇 건이 성공했는지, DB에 무엇이 남았는지 눈으로 확인했다
- 왜 그렇게 됐는지 말로 설명할 수 있다

**설명할 질문**

- 두 스레드가 동시에 지나갈 때 정확히 **어느 줄**에서 문제가 생기나?
- "조회해서 없으면 INSERT"가 왜 안전하지 않은가?
- 트랜잭션을 걸었는데도 막히지 않는 이유는? (격리 수준이 무엇을 보장하고 무엇을 안 하나)

> 💡 이 Step을 건너뛰면 안 된다. **깨지는 걸 직접 본 사람과 남의 코드를 읽은 사람은 다르다.**
> Step 2의 모든 판단이 여기서 본 것에 근거한다.

## Step 2 — 막는다

- [ ] 완료

**목표**: Step 1의 테스트를 통과시킨다.

**대안을 최소 셋 비교한다** (이름만 적어둔다 — 고르는 건 당신 일이다)

```
DB 유니크 제약        비관적 락(SELECT ... FOR UPDATE)        낙관적 락(@Version)
```

**완료 조건**

- Step 1의 테스트가 통과한다
- **고르지 않은 대안들도** 왜 안 골랐는지 말할 수 있다
- `ai_docs/DECISIONS.md`에 기록했다 — 특히 **포기한 것**
- 보호 코드를 되돌리면 테스트가 **다시 실패한다** (확인했다)

**설명할 질문**

- 세 대안이 각각 **어디에서** 막는가? (애플리케이션 / DB 엔진 / 스키마)
- 유니크 제약으로 막으면 왜 예외 처리가 달라지는가?
- 낙관적 락을 고르면 실패한 요청은 어떻게 되는가? 사용자에게 뭐라고 답하나?
- 락을 잡는 동안 DB 커넥션을 쥐고 있는가? 그게 왜 문제가 될 수 있나?
- 선점이 만료되거나 취소되어 좌석이 다시 팔려야 할 때, 고른 방법이 그걸 허용하나?

## Step 3 — 선점 만료를 다룬다

- [ ] 완료

**목표**: 결제되지 않은 선점을 만료시켜 좌석을 다시 팔 수 있게 한다.
그리고 **만료와 결제가 같은 선점에 동시에 일어나는 경합**을 막는다.

**대안을 최소 셋 비교한다** (만료를 언제 판정하나)

```
조회·요청 시점에 판정        주기적 스케줄러        TTL이 있는 저장소
```

**재현**: 만료 시각 직전에 들어온 결제와 만료 처리를 동시에 실행한다.
만료된 좌석을 다른 사용자가 선점하는 것과 원래 사용자의 결제가 겹치는 경우도 만든다.

```
기대: 둘 중 하나만 이긴다 (만료되고 결제 거절 / 결제되고 만료되지 않음)
실제: ?
```

**완료 조건**

- 유효 시간이 지난 선점의 좌석이 다시 선점 가능해진다
- 만료와 결제가 겹치는 **실패하는 테스트를 먼저 봤고**, 이제 통과한다
- "결제는 성공했는데 좌석이 남의 것" 또는 "한 좌석에 확정 예약 둘"이 생기지 않는다
- 보호 코드를 되돌리면 테스트가 **다시 실패한다** (확인했다)
- 만료 방식 선택을 `DECISIONS.md`에 기록했다

**설명할 질문**

- 고른 방식에서, 만료 시각이 지났지만 아직 처리되지 않은 선점은 어떤 상태인가? 그 사이에 누가 무엇을 볼 수 있나?
- 결제가 만료 1ms 전에 시작해서 1ms 후에 커밋되면 누가 이겨야 하나? 그 판정은 **누구의 시계**를 기준으로 하나?
- Step 2에서 고른 보호 장치가 이 경합도 막아주나? 아니라면 무엇이 달라서인가?
- 선점 유효 시간을 5분에서 10분으로 늘리면 무엇이 좋아지고 무엇이 나빠지나?

## Step 4 — 모듈을 가른다

- [ ] 완료

**목표**: 단일 패키지를 `reservation` / `payment` / `ticket` 셋으로 나눈다.

`ticket`은 **발권**을 맡는다 — 확정된 예약에 티켓을 발급하고 조회를 제공한다.

모듈 패키지는 `com.ticketing` **바로 아래**에 둔다 — Spring Modulith가 모듈로 인식하는 위치다.
지금은 **패키지만** 나눈다. 강제 수단은 Step 5다.

**재현**: 나누는 과정 자체가 문제를 드러낸다. 나누다 보면 반드시 막힌다 —
그 막힌 지점을 적어두라. Step 5·6의 재료다.

**완료 조건**

- 세 패키지로 나뉘었고 테스트가 그대로 통과한다
- **나누면서 막힌 지점을 목록으로 적었다** (어느 클래스가 양쪽에 걸쳤나)
- 각 모듈이 소유하는 테이블을 정했다

**설명할 질문**

- 예약과 결제의 경계를 어디에 그었나? 좌석 재고와 선점은 누구 것인가?
- `Reservation`이 `Payment`를 참조하나, 아니면 반대인가? 왜?
- 예매 조회 응답에 결제·티켓 정보가 함께 나가야 한다면, 그 조립은 누가 하나?
- 나누기 전과 후에 **트랜잭션 경계**가 달라졌는가?

> 💡 여기서 "경계"가 처음 아프다. 그 아픔이 Step 5~6의 동기다.

## Step 5 — 경계를 강제한다

- [ ] 완료

**목표**: `AGENTS.md`의 경계 규칙 ①~④를 **Spring Modulith 테스트가 지키게** 만든다.
규칙 ⑤는 Modulith가 보지 못한다 — 어떻게 지킬지 정한다.

```
ApplicationModules.of(...).verify()     어기면 테스트가 실패한다 (컴파일은 된다)
```

**재현**: 규칙 ①~④를 하나씩 **일부러 어겨본다.** 컴파일은 되는 것을 확인하고, 테스트가 실패하는지 본다.
실패하지 않는 규칙이 있으면 그 규칙은 아직 존재하지 않는 것이다.

**완료 조건**

- Spring Modulith를 붙였다 (Boot 4.1과 호환되는 버전인지 `./gradlew dependencies`로 확인)
- 규칙 ①~④를 각각 어겨봤고, **넷 다** 테스트가 실패한다 (직접 확인)
- 검증 테스트는 Docker 없이 돈다
- 규칙 ⑤를 지킬 방법을 정했다
- `DECISIONS.md`에 기록했다 — Gradle 멀티모듈 대신 Modulith를 고른 이유와 **포기한 것(컴파일 시점 강제)**
- 이벤트 기능(`@ApplicationModuleListener`, Event Publication Registry)은 아직 쓰지 않았다

**설명할 질문**

- `verify()`가 **기본으로** 잡는 것과 **설정해야** 잡는 것은 각각 무엇인가?
- Modulith는 무엇을 근거로 "모듈"과 "공개 API"를 판단하나? 패키지를 잘못 두면 무엇이 그냥 통과하나?
- 위반이 컴파일에서 막히는 것과 테스트에서 잡히는 것은 개발할 때 어떻게 다른가? Gradle 멀티모듈을 골랐다면 무엇을 더 얻었나?
- 규칙 ⑤는 왜 Modulith가 잡지 못하나?
- 루트 패키지(`app` 역할)가 모든 모듈을 조립해도 괜찮은 이유는?

## Step 6 — 모듈 간 통신을 정한다

- [ ] 완료

**목표**: `reservation`이 `payment`를 못 보는데 결제를 시켜야 한다.
결제가 확정되면 `ticket`이 발권해야 한다. **인터페이스를 누가 소유하나?**

정답이 하나가 아니다. 최소 셋을 비교한다.

```
A. 단방향 직접 의존        reservation → payment
B. DIP (의존 역전)         소비자가 인터페이스 소유, 구현 어댑터는 app에
C. 애플리케이션 이벤트      Spring ApplicationEvent (Modulith의 @ApplicationModuleListener 포함)
```

**완료 조건**

- 결제 요청과 발권 각각에 방식을 골라 구현했고 테스트가 통과한다
- 셋의 트레이드오프를 표로 적었다
- `DECISIONS.md`에 기록했다 — **포기한 것 포함**
- 트랜잭션 경계가 어떻게 되는지 그림으로 그렸다

**설명할 질문**

- B로 하면 `reservation`과 `payment`가 서로를 전혀 모르게 된다. 그 대가는?
- C(이벤트)로 하면 **같은 트랜잭션인가?** `@TransactionalEventListener`의 `phase`는 무엇을 바꾸나?
- `@ApplicationModuleListener`는 `@EventListener`·`@TransactionalEventListener`와 무엇이 다른가? 기본값 그대로 쓰면 트랜잭션 경계가 어떻게 되나?
- 결제가 실패하면 예약은 어떻게 되나? **여기서 롤백 한 줄로 끝나는 것을 확인하라** —
  예약과 결제가 서로 다른 서비스였다면 무엇이 필요했겠나?
- 결제 요청과 발권에 같은 방식을 골랐나? 다르다면 무엇이 달라서인가?
- 발권이 실패하면 결제와 예약 확정도 되돌려야 하나?

## Step 7 — 외부 결제(PG)를 붙인다

- [ ] 완료

**목표**: 결제를 내부 처리에서 **외부 HTTP 호출**로 바꾼다. 처음으로 "남의 시스템"이 등장한다.

PG는 가짜로 만든다 (별도 프로세스 또는 WireMock). 응답을 마음대로 늦추고 실패시킬 수 있어야 한다.

**완료 조건**

- 정상 결제가 외부 호출을 거쳐 성공한다
- **HTTP 호출이 트랜잭션 밖에 있다** — 왜 그래야 하는지 설명할 수 있다
- 타임아웃이 설정되어 있다 (기본값에 의존하지 않는다)

**설명할 질문**

- HTTP 호출을 트랜잭션 안에 두면 무슨 일이 생기나? PG가 3초 끌면?
- 호출 실패와 호출 타임아웃은 다른가?
- PG 응답을 기다리는 사이 선점이 만료되면 어떻게 되나?
- 여기서 처음으로 "롤백으로 해결되지 않는 것"이 생겼다. 무엇인가?

---

## Step 8 — 결과를 모르는 결제를 다룬다

- [ ] 완료

**목표**: Step 7에서 생긴 진짜 문제. **"보냈지만 결과를 모른다".**

**재현**: PG 응답을 타임아웃시킨다. 그 순간 우리가 아는 것과 모르는 것을 적어보라.

**완료 조건**

- "보내지 못했다"와 "보냈지만 결과를 모른다"를 **코드에서 구분**한다
- 타임아웃 후 **재전송하지 않는다.** 대신 조회한다
- 조회로 확인된 건이 흐름에 되돌아온다
- 클라이언트 재시도에 대한 멱등성이 있다 (같은 결제 요청 두 번 → 결제 하나)
- 각 경우를 재현하는 테스트가 있다

**설명할 질문**

- 타임아웃 났을 때 바로 재전송하면 무슨 일이 생기나?
- 바로 취소(환불)하면 무슨 일이 생기나?
- 결과를 모르는 동안 선점 유효 시간이 지나면 좌석은 풀어야 하나, 붙잡아야 하나?
- 멱등성 키를 어디에 저장했나? 언제 지우나? **키 선점 후 죽으면** 어떻게 되나?
- 우리 DB의 제약이 아니라 **PG의 약속**에 기대는 부분은 어디인가?
- Modulith의 Event Publication Registry는 이 문제의 어디까지를 해결하나? "결과를 모른다"도 해결하나?

> 💡 여기서 Outbox·보상·멱등성이 **처음으로 정말 필요해진다.** 그리고 필요한 자리는
> 내부 경계가 아니라 **외부 경계 한 곳뿐**이다.
>
> Event Publication Registry는 **문제를 먼저 겪은 뒤** 대안 중 하나로 비교한다. 미리 깔아두면 이 Step에서 겪을 것이 사라진다.

## Step 9 — 취소와 환불을 붙인다

- [ ] 완료

**목표**: 확정된 예약을 취소한다. PG에 환불을 요청하고, 티켓을 무효화하고, 좌석을 다시 판다.
취소는 회차 시작 전 정해진 기한까지만 가능하다.

**재현**

```
환불 요청이 실패하거나 타임아웃된다
같은 예약에 취소 요청이 동시에 2건 들어온다
```

**완료 조건**

- 취소하면 예약·티켓·좌석이 함께 바뀌고 환불이 요청된다
- 취소 기한이 지난 예약은 거절된다
- 같은 예약에 취소가 두 번 와도 (동시 요청 포함) **환불은 한 번**이다
- 환불 실패·결과 모름을 재현하는 테스트가 있고, 그 예약이 **어떤 상태로 끝나는지** 정해져 있다
- 환불이 끝나기 전에 좌석을 풀지 말지를 `DECISIONS.md`에 기록했다

**설명할 질문**

- 좌석을 다시 파는 시점은 환불 요청 전인가, 환불 확인 후인가? 각각 어떤 사고가 날 수 있나?
- Step 8에서 만든 "결과를 모르는 결제" 처리를 환불에 그대로 쓸 수 있나? 무엇이 다른가?
- 환불이 끝내 실패하면 시스템이 스스로 끝낼 수 있는 일인가? 누가 알아야 하나?
- 결제 결과 조회로 확정 처리가 도는 중에 취소 요청이 오면 어떻게 되나?

## Step 10 — 인스턴스를 2개 띄운다

- [ ] 완료

**목표**: 같은 앱을 두 포트로 띄우고 같은 DB를 보게 한다. **Step 2·3의 보호가 아직 유효한가?**

**재현**

```
두 인스턴스에 동시에 같은 좌석을 선점 요청한다
두 인스턴스가 같은 선점을 동시에 만료 처리한다 (Step 3의 방식에 해당하는 경우)
```

**완료 조건**

- 두 인스턴스에서도 이중 선점이 막힌다
- 만료 처리가 두 인스턴스에서 겹쳐도 결과가 한 번 실행한 것과 같다 — 해당 없다면 **왜 해당 없는지** 적었다
- 막히는 **근거**를 말할 수 있다 (무엇이 지켜주고 있는가)
- 필요하다면 분산 락을 도입했고, **왜 필요해졌는지** 기록했다

**설명할 질문**

- Step 2·3에서 고른 방법이 인스턴스 2개에서도 통하나? 통하면 왜, 안 통하면 왜?
- 분산 락이 **필요한 경우**와 **필요 없는 경우**를 가르는 기준은?
- 분산 락과 DB 락을 둘 다 잡는다면 각각 무엇을 막는가?
  **"정합성이 더 좋아서"는 왜 틀린 답인가?**
- Redis가 죽으면 예매가 멈춰야 하나, 계속돼야 하나? 그 판단의 기준은?

## Step 11 — 인기 공연으로 부하를 준다

- [ ] 완료

**목표**: 좌석 하나가 아니라 **인기 공연의 한 회차**에 몰리는 부하. 처리량 상한을 측정한다.

**완료 조건**

- 측정 조건을 적었다 (동시 사용자, 좌석 분포, 실행 환경)
- **락 보유 시간**을 쟀다 — 그게 곧 처리량 상한이다
- 병목이 무엇인지 숫자로 말할 수 있다 (락? 커넥션 풀? CPU?)
- 개선했다면 **같은 조건에서** 전후를 쟀다
- 대기열을 도입했다면, **측정값으로** 그 필요를 보였다

**설명할 질문**

- 락 보유 시간 p50이 20ms면 초당 몇 건인가? 서버를 늘리면 그 숫자가 변하나?
- TPS 하나만으로 "좋아졌다"고 말하면 안 되는 이유는?
- 첫 실행을 버려야 하는 이유는? (JVM·커넥션 풀·캐시)
- 대기열은 처리량 상한을 올리나? 올리지 않는다면 무엇을 해결하나?

> ⚠️ **성능은 노트북에서 재지 않는다.** 부하 생성기와 측정 대상이 같은 CPU를 두고 싸운다.
> 측정 환경이 없으면 숫자를 적지 말고 "아직 측정하지 못했다"고 적는다.

## Step 12 — 어느 모듈을 서비스로 떼어내야 하나 ★

- [ ] 완료

**목표**: 이 프로젝트의 결론. **코드를 쓰는 Step이 아니라 답하는 Step이다.**

각 모듈에 대해 판단한다.

```
떼어내야 하는 이유가 있나?   독립 배포 / 독립 스케일 / 다른 저장소 / 팀 분리 / 장애 격리
떼어내면 무엇을 잃나?        트랜잭션 / 조회 조립 / 운영 복잡도
떼어내려면 무엇을 고쳐야 하나?  ← Step 6의 선택이 여기서 값으로 드러난다
```

**완료 조건**

- 모듈별로 "뗀다 / 안 뗀다 / 아직 모른다"를 근거와 함께 적었다
- **측정이나 구체적 사실**에 근거한다. "확장성이 좋아서"는 근거가 아니다
- 하나를 골라 **떼어내는 데 드는 비용을 견적**냈다 (고쳐야 할 파일 목록)
- 판단과 근거를 `DECISIONS.md`에 남겼다

**설명할 질문**

- 모듈러 모놀리식으로 시작한 것이 옳았나? 무엇을 얻고 무엇을 못 얻었나?
- 이 프로젝트에서 **정말 필요했던** 분산 장치는 어느 것이었고, 어디에서 필요했나?
- "모듈러 모놀리식으로 시작해서 필요한 것만 떼어내라"는 조언을 실제로 해본 소감은?

## Step 13 — `user`가 필요해졌다

- [ ] 완료

**목표**: 예매 확정·취소 알림에 이메일이 필요하다. **모두가 참조하고 싶어하는 모듈**을 어떻게 붙이나.

이게 모듈러 모놀리식이 실무에서 무너지는 가장 흔한 경로다 —
`user`가 공통 모듈이 되고, `common`으로 이름이 바뀌고, 경계가 사라진다.

**진행 순서** (이 순서를 지키는 게 이 Step의 내용이다)

1. **규칙 ②를 Modulith 테스트로 먼저 강제한다** — `user`는 업무 모듈을 의존할 수 없다
2. 규칙을 어기는 코드를 짜서 **테스트가 실패하는지 확인한다**
3. `user` 모듈을 추가하고 `notification`이 쓰게 한다
4. *"`user`를 서비스로 떼어낸다면 무엇을 고쳐야 하나"*를 적는다 → **DIP로 뒤집을 값어치의 견적**

**완료 조건**

- `user` 모듈이 있고 규칙 ②가 테스트로 강제된다
- `user`에 업무 규칙이 **없다** (`canReserve()` 같은 게 없다)
- `UserId`는 `shared-kernel`에 있고 도메인 모듈은 인증을 모른다

**설명할 질문**

- `user`를 여럿이 의존하는 것은 왜 문제가 아닌가? 언제부터 문제가 되나?
- "이 사용자가 예약할 수 있나"는 누구의 규칙인가? 왜?
- `shared-kernel`에 무엇까지 넣어도 되나? 그 경계를 어떻게 지키나?
- 예약 이벤트에 이메일을 실어 보내는 방법도 있다. 의존과 데이터 중복 중 무엇을 골랐나?
